# 向量模块说明

## 模块边界

- `paper_vector_service.py`：复用 `src.load_data` 读取和校验论文、taxonomy，再解析名称，构造正文、论文上下文及向量专用 metadata，以稳定论文编号关联检索结果。不存在的编号、未定义的分类/类型/标签明确报错。
- `lifecycle.py`：通过 `paper_vector_service_lifespan()` 提供模块内部管理的延迟服务句柄，负责首次创建、生命周期锁和关闭清理。
- `store.py`：保存和检索流程的协调者，管理操作锁、metadata 索引、只读检索快照、缓存失效与相似度计算；不解释论文类型或标签字段，也不直接操作分片文件。
- `chunking.py`：纯函数 `chunk_text()` 和 `build_embedding_inputs()`，负责分块参数校验、正文切分及通用上下文前缀，不读文件、不调用模型、不解释论文信息。
- `jsonl_storage.py`：`JsonlStorage` 负责分片发现、签名、逐行读取、行数统计和追加写入；不管理缓存、网络或相似度，也不自行加操作锁，调用方 VectorStore 统一协调。
- `embed_client.py`：调用嵌入服务，检查响应结构、数量、非空一致维度及有限数值；返回条目带 `index` 时，要求全部条目都有有效且唯一的 0 起始编号并恢复输入顺序，不带编号时保留响应顺序。它同时管理 HTTP 客户端生命周期。

调用流程为 `PaperVectorService → VectorStore → chunking / EmbedClient / JsonlStorage`。`src.template.Paper` 仅保存已解析数据；向量 metadata 在 service 的 `_build_metadata()` 中构造，不再由通用论文数据类负责。

本地每行只保存 `vector` 和 `metadata`，后者仅含 `title`、`index`。正文和上下文不写入 JSONL，不兼容历史 `paper_id` 字段。

## 分块和上下文

`chunking.chunk_text()` 在处理文本前验证 `size`、`overlap` 是整数且不是布尔值，并要求 `size > 0`、`0 <= overlap < size`。这能避免错误配置使分块起点无法前进。

service 将内容概述和精细总结作为待分块正文，另构造标题、中文文献类型和中文标签组成的上下文。`VectorStore.save(text, metadata, context=...)` 调用 `build_embedding_inputs()` 为每个正文分块添加相同前缀，再交给 EmbedClient；通用 store 不解析前缀含义。`CHUNK_SIZE` 控制正文字符数，不包含前缀，也不是 tokenizer 的 token 上限。此轮仅调整代码职责，正文拼接、前缀内容及分块方式保持一致。

新策略只影响后续生成。修改代码不会自动重新嵌入已有论文；相同 metadata 仍会被跳过。需要使整个库采用一致策略时，应另行明确重建，避免混合新旧文本构建策略。

## 内存缓存

缓存属于各个 VectorStore 实例，不另行生成持久缓存文件：

1. metadata 索引：首次使用时读取所有分片，后续根据分片签名复用。成功保存后加入新 metadata，并更新签名，不为每篇论文重新解析整个库。
2. 检索快照：缓存向量矩阵、每个向量的范数、metadata 和已序列化的判重键。重复查询只计算查询向量和相似度，不重新解析 JSONL、构造矩阵或计算库向量范数。
3. 失效检查：每次访问检查匹配分片的文件名、字节大小、纳秒修改/状态时间和文件标识。分片新增、删除或观察到文件信息改变时，下次访问会刷新相应缓存；读取前后签名不一致时不发布新缓存。
4. 保存成功后立即使检索快照失效，下次检索再重建。写入异常会清空内存缓存，但不回滚磁盘文件。
5. VectorStore 自己通过同一把可重入锁串行保护完整的 save()、retrieve() 和 close()，包括嵌入请求、判重、分片读写、缓存和相似度计算。路由不包裹存储操作锁，直接使用 store 的调用方也获得相同保护。对外返回 metadata 副本，避免调用方修改缓存。

签名检查不是内容哈希，也不是跨进程锁或事务机制。当前仍要求单写入者；在签名更新的同时发生外部写入不能获得事务保证。缓存会驻留整个向量矩阵，分片行数上限不等于检索内存上限。

文件变化检测集中在 store 的 `_storage_state()`，流式读取、读取后一致性检查及对应失败清理集中在 `_read_consistent_records()`。metadata 索引和矩阵快照均完整消费该读取器，前者不保留全部向量。私有缓存助手要求调用方已持有 store 的操作锁，不再重复加锁；公共 `save()`、`retrieve()`、`close()` 仍覆盖完整操作。EmbedClient 校验远程响应，store 校验本地文件读入后形成的矩阵与查询维度，两者位于不同的数据入口。

PaperVectorService 的路径统一使用 `Path`；`_load_paper()` 先通过资料读取层校验，再构造内部 Paper。`_build_text()` 依赖这个内部约定，保留实际 Markdown 读取失败和正文为空的检查，不重复校验已经确认的概述字段。正文、上下文内容和稳定编号映射方式保持不变。

## 客户端生命周期

VectorStore 创建并拥有 EmbedClient 和 JsonlStorage；PaperVectorService 只通过 VectorStore 保存、检索和关闭，不直接访问嵌入客户端。

- `PaperVectorService.close()` 调用 `VectorStore.close()`；store 在操作锁内等待进行中的存储操作完成，标记关闭、释放缓存并调用 `EmbedClient.close()`。关闭为终止操作，重复关闭安全。
- 关闭后的 `create_vector()`、`retrieve()` 或 `EmbedClient.embed()` 明确报错，不自动重新创建连接。
- 再次使用时创建新实例。两个类均支持 `with`，退出时关闭；路由应用退出时调用 service 的公开关闭接口，并清除实例引用。
- store 在其他初始化步骤全部完成后才创建 EmbedClient，避免后续初始化失败导致客户端泄漏。

服务延迟创建和关闭时的生命周期锁位于 `lifecycle.py` 内部，取得实例引用后释放该锁，再将操作交给 PaperVectorService；它不包裹 store 的检索或写入。关闭后的句柄禁止重新创建服务。每次应用 lifespan 使用独立句柄，不使用全局单例。

routes 只通过 `async with paper_vector_service_lifespan(...) as service` 接入生命周期，将当前句柄提供给请求转发函数；退出上下文时，semantic_search 模块在线程中关闭服务。routes 不持有生命周期锁，也不直接调用 close。普通浏览不会导入 store、NumPy、EmbedClient 或创建嵌入客户端。需要直接进行批量向量操作时，也可继续用 `with PaperVectorService(...) as service` 管理一个独立实例。

## 写入中断恢复方案（仅设计，本轮未实现）

### 目标和不变量

一篇论文的全部分块为一次事务，即使横跨多个 `vectors_N.jsonl`，也必须全部提交或全部回滚。读者不应看到未完成的事务，重试不应把部分分块当成成功。保留现有向量记录结构，不在 metadata 中加入事务号、状态或哈希。

建议在向量目录中另设 `.transactions/<transaction_id>/`，保存暂存 JSONL 和事务状态。状态文件至少记录 metadata 键、预期总行数、各分片的原字节长度、计划追加长度、目标文件名、是否为新文件及内容校验摘要。新增论文使用现有稳定编号，事务号另用独立随机 ID。

### 一次保存的顺序

1. **生成和暂存。** 完成全部嵌入及数量、维度、有限数值检查，将本次完整记录写入事务暂存文件。生成失败不修改正式分片。
2. **取得跨进程独占锁。** 所有写入者必须使用同一把目录级文件锁。先恢复遗留事务，再检查已提交 metadata 是否存在，避免两个生成任务重复提交。
3. **制定追加计划。** 检查现有分片末行是完整 JSON，按行数上限规划每个目标分片；记录修改前的字节偏移和新增文件列表。不能通过猜测换行位置修复未知来源的历史损坏。
4. **持久化准备状态。** 把 `PREPARED` 状态写到临时状态文件，flush、fsync 后原子替换为正式状态文件，确保在修改分片之前已有恢复依据。目录元数据持久化需要按 Windows 和实际文件系统能力实现，不能仅依赖 Python 缓冲区刷新。
5. **追加完整数据。** 按计划追加暂存记录，逐个分片 flush、fsync，并核对长度、行数及摘要。任何异常都进入回滚流程，不能返回 `saved=True`。
6. **提交。** 所有目标分片持久化成功后，通过临时文件加原子替换，将该事务状态改成 `COMMITTED`；此标记是唯一提交点。
7. **刷新缓存并清理。** 提交后更新 metadata 索引、失效检索快照。清理暂存数据；清理失败可留待恢复，不应再次追加数据。最后释放锁并返回成功。

### 恢复规则

必须在启动读取、判重以及继续写入之前取得恢复锁并处理遗留状态：

| 磁盘状态 | 恢复动作 |
| --- | --- |
| 只有暂存文件，没有准备状态 | 正式文件尚未授权修改，清理或保留暂存以便重试 |
| `PREPARED`，未提交 | 将已有分片截断到记录的原字节偏移，移除本事务创建的新分片，持久化回滚后再允许重试 |
| `COMMITTED` | 不重复追加；核对已提交数据，完成缓存刷新或暂存清理 |
| 已提交记录与分片长度/摘要矛盾 | 停止自动处理并报告损坏，不能静默跳过或宣称恢复成功 |

回滚涉及截断和删除，必须先验证所有目标的最终绝对路径位于配置向量目录中，且确实属于该事务；锁内不得有其他写入者追加到待回滚区域。回滚也需可重复执行，完成标记写入前崩溃时仍能再次恢复。

### 读取一致性

读者在加载或刷新快照时取得与写入者协调的共享锁；不支持共享锁的平台先统一使用独占锁。检测到遗留事务时先在独占锁下完成恢复，再读取已提交数据。读入内存的完整快照可以在释放锁后继续服务查询。单纯存在 metadata 或末行有换行符，都不能充当事务提交证明。

### 返回值和旧数据

- `saved=True`：完整事务已经提交，而非只写入了至少一行。
- `saved=False`：已有完整、已提交且符合当前判重策略的记录。
- 生成、提交或恢复失败：明确报错，并记录论文编号与失败阶段；批量调用方可报告成功和失败清单。
- 方案不能自动证明历史分块是否完整。首次启用需要审计现有库，或从已核对资料建立完整新库；不能把旧库里任一条相同 metadata 当成已提交事务。

本机文件锁不能阻止另一台机器通过同步软件覆盖文件；多设备同步目录应限定一个写入端，或将写入集中到单一服务。还应覆盖磁盘写满、各提交阶段中断、跨分片提交、重复恢复、并发读写及失败重试等验证场景。
